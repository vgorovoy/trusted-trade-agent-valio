The implemented MCP server uses stdio, launched locally by an MCP client. This website does not expose a hosted HTTP MCP endpoint.

Tools include search_products, get_product, get_offers, plan_need, find_substitutes, place_order, get_order, explain_order and get_valio_keys. Human approval remains a separate human action.

Review quantities before ordering

These are review responsibilities, not a claim that the model knows the kitchen's true demand.

  1. Establish the baseline. Supply service counts, recipe amounts, yield assumptions, usable stock and dated receipts. Without those facts, a dish name does not establish a reliable required quantity.
  2. Separate pack size from quantity. For example, 10 packs × 500 g means 5 kg. Compare the proposed sales units and pack-rounded supply with the reviewed need.
  3. Resolve missing or conflicting facts. Ask the kitchen for absent quantities, units or delivery dates. Do not treat a default or a guessed portion size as a fact from the source.
  4. Check both shortage and surplus. Compare the basket with the supplied baseline. A person must review an unexplained difference before ordering; a low price or an in-budget total does not establish that the quantity is right.
The current UI supports editable draft review and exact-cart confirmation. It does not provide a complete automatic reconciliation of every basket against a recipe/inventory baseline, forecast demand, or prevent all human input errors.

Read the evidence without overstating it

Model comparison keeps attempted cases, provider errors, raw scores and annotations visible. Three narrow cases and one attempt per model are preliminary evidence. Zero recorded harness interventions does not prove that the harness rescued errors.

Storage: Aiven PostgreSQL + SQLite

Signed offers, orders and receipts, Valio reviews, and the hash-chained audit log use Aiven for PostgreSQL over TLS when a database URL is configured and local mode is off. The catalogue and FTS5 search stay in a local SQLite file.

Without a database URL, or with TTA_LOCAL=1 or --local, order and audit state use SQLite. A frozen TTA_DEMO_CLOCK also uses SQLite unless the deployment opts into its own PostgreSQL schema with TTA_STORE_SCHEMA (for example demo_20261114), so frozen demo timestamps never mix with other records. Every writer shares one hash chain through a PostgreSQL advisory lock. A configured PostgreSQL connection failure is reported; it does not silently switch databases.
